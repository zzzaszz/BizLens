### 澄清"没配凭据为什么能索引到私有仓库"（同日）

用户指出项目「444」（`github.com/zzzaszz/404-forum`）是私有仓库，却没有任何凭据也能索引成功。
实测澄清：

- 匿名访问 `api.github.com/repos/zzzaszz/404-forum` 返回 404 → 仓库确实是私有的。
- `GIT_TERMINAL_PROMPT=0 git ls-remote <url>` 仍成功，返回的 commit 与库里记录一致。
- 本机 `credential.helper=store`，`~/.git-credentials` 中存在 github.com 条目。

结论：克隆成功是因为 `git` 静默使用了**运行机器上存储的凭据**，而不是仓库公开。
`credential_ref` 空 ≠ 匿名访问，因此该字段不构成任何访问控制——
**任何注册用户都能借机器凭据克隆并索引自己无权访问的私有仓库**，后续已通过切断机器凭据继承和按项目配置 Git 访问令牌修复。

同时修正了两处基于错误假设的文案：列表「Git 凭据」列不再写「公开仓库可留空」。

### 修复内网 GitLab 克隆报 502（同日）

用户报告内网项目 `http://git.inksdev.com/mfomspad/mf-omspad.git` 克隆报
`The requested URL returned error: 502`。

定位：502 响应带 `Proxy-Connection`、无 `Server` 头 → 是**链路上的代理**返回的，不是 GitLab。
机器上有 Clash（`HTTP_PROXY=127.0.0.1:7890`），而全局 git 配置里写着 `http.noproxy git.inksdev.com`
让 git 平时绕过代理；直连 `curl --noproxy '*'` 能拿到 GitLab 的 401，说明服务本身健康。

**根因是上一轮凭据隔离引入的回归**：清空 git 配置以切断凭据继承时，把 `http.noproxy` 这条例外一起清掉了，
却保留了 `HTTP_PROXY`/`HTTPS_PROXY` 环境变量，于是内网地址被送进 Clash。

修复：代理同样改为不继承、由服务端显式声明——`applyIsolatedGitEnv` 先移除全部继承的代理变量，
再按 `BIZLENS_GIT_PROXY` / `BIZLENS_GIT_NO_PROXY` 注入，两者都不设则直连；
连不上时的失败原因里会提示这两个变量。

验证（详见测试文档 5.8）：不给代理配置时内网报「需要凭据」（401）而非 502；
配上 `BIZLENS_GIT_PROXY` + `NO_PROXY` 后内网仍直连、github 走代理成功。

### 修复索引状态不刷新（同日）

用户报告：服务端已报索引失败，`/projects` 却一直显示「索引中」。

查证：库里 `status` 已是 `FAILED`、`updated_at` 即失败落库时刻；全新标签页加载也显示「失败」——
后端与接口都没问题。**真正原因是页面只在进入时加载一次**：点完「排队索引」拿到 `QUEUED`，
之后索引在后台跑完/失败，页面不再去问，于是永远停在「索引中」，必须手动刷新。

修复：`CodeProjects.vue` 加轮询——只要有项目处于"正在索引"（复用 `isIndexRunning` 的 10 分钟时间窗判定，
避免卡死导致永久轮询），每 3 秒静默刷新；跑完即停；轮询走 quiet 模式不动 loading，组件卸载清定时器。
实测：点排队后 1.5s 显示「索引中」→ 4.5s 自动变「已就绪」，全程未手动刷新。

顺带：分支名写错时的提示改为「分支不存在：……（Git 默认分支可能是 main，也可能是 master）」，
用户这次正是把 master 的仓库填成了 main。

### 修复两处资源泄漏（同日）

起因是评估"项目越来越多会不会越来越占空间"。数据库那边实测下来是线性、可预算的
（单切片行 624 字节、单文件约 12 KB 落盘、1000 文件仓库约 12 MB），但抓到两处只增不减的泄漏：

**一、索引临时工作区（实测 25 个目录 / 309 MB，最早的是两周前）**
清理逻辑本来就写在 `finally` 里，**从来没成功过**：git 在 Windows 上把
`.git/objects/pack` 下的 `.pack/.idx/.rev` 设成只读，`Files.deleteIfExists` 遇到只读文件
直接抛 `AccessDeniedException`（不像 `rm` 会先 chmod），目录删不空，整棵工作区就留下了。
修复：删之前先 `setWritable(true)`（Linux 空操作）；另加兜底——启动时与每次索引前扫临时目录，
清掉超过 1 小时仍未删掉的残留（跳过本进程在用的）。
实测：修复前启动只删掉 1 个、14 条 AccessDeniedException；修复后清理 14 个、释放约 235 MB；
再走一次真实索引，`finally` 里就删干净了。

**二、Redis 热上下文永不失效**
`setCacheObject` 未设 TTL，每个聊过的会话永久占内存（删会话会清、关闭会话不会）。
修复：TTL 7 天、写入续期。实测新写入的 key `TTL = 604791` 秒。

另把这两项的单位成本与多实例注意事项写进 README「容量与清理」。

### 修复索引一直「索引中」+ 索引进度可见（同日）

用户报告 `omspad` 一直显示「索引中」。查证：库里状态 `INDEXING`、`updated_at` 六分钟没动、
**没有任何 git 进程**、那次的工作区留下一份 4.5MB 的半截克隆——是**服务在索引途中被重启**
（`finally` 不执行、状态没回写），而系统没有任何机制收敛这种状态。

修复：
- **心跳**：运行期每 30 秒推进 `updated_at`，让"是否还在跑"可判断；
- **启动收敛**：启动时把超过 180 秒无心跳的 `QUEUED/INDEXING` 置为 `FAILED`，原因写明「索引任务被中断…」；
- **中断识别**：前端对"索引中但无心跳"显示灰色「索引中断」，不再假装还在跑；
- **进度显示**：索引中「已用 X，预计还需约 Y」（Y 取自 `last_index_ms`，即上次成功耗时）、
  完成「X 完成」、失败「X 失败」。新增列 `last_index_ms`（`migration-20261007-indexduration.sql`）。

自测中发现并修掉一个自己引入的 bug：第一版用浏览器时钟减 `updated_at`，而后者是数据库时钟写的，
本机差 13 秒，表现为"刚点下去就显示已用 14 秒"。改为 SQL 用 `now() - updated_at` 算好 `elapsedMs` 返回。

### 新增「一键索引排队」（同日）

代码项目页表头加「一键索引排队」按钮，点一下把全部项目重新排队索引。

- 后端新增 `POST /ai/project/indexAll`：一次请求处理全部项目（前端不必发 N 个请求），
  规则与单个重排一致——**正在索引的跳过**（同一项目并发跑两个索引会互相覆盖切片），
  返回 `{total, queued, skipped, skippedNames}`。
- 前端按钮带确认框（逐个重排会重新克隆 + 重写切片，属重操作），完成后提示排队与跳过数量；
  批量执行期间每行各自显示「已用/预计」，走的还是上一轮的进度显示。

顺带修掉一处前后端口径不一致：后端重排守卫原本是 10 分钟时间窗，而心跳与前端已是 180 秒，

跑完 4 个 READY 并各自记录耗时（999 文件/15s、215 文件/4s 等），1 个因未配令牌失败且不影响其它项目。

### 修复 AI 答错接口权限问题（同日）

用户反馈问 `/system/SYSM03B4/getEntity` 的接口权限时，AI 回答"片段里找不到这个接口、无法确认权限"，
但该接口确实存在且带 `@PreAuthorize(hasPermi = "PiPermission.List")`。

查出 5 个缺陷并全部修掉：

1. **方法切片的行区间不含上方注解**——正则从 `public` 起匹配，上面几行注解全被丢掉，
   所以"这个接口要什么权限"这类问题**永远查不到答案**。改为向上把相邻注解/注释行纳入切片起点。
2. **FILE 级切片只取 800 字符**，控制器文件常常正好切在第一个方法之前，看起来像"这个类没有方法"。提到 2400。
3. **`^\s*` 会吃进前一行的空行**，导致记录的行号落在空行上、取出的片段只有一个换行符
   （svc-sys 里 145 个这种残片）。四个正则的行首改成 `^[ \t]*`。
4. **召回排序按片段长度升序**，把最短（往往就是上述残片）排在最前、占满 6 个名额。
   改为长度降序，并加"符号名精确同名"加成（`getEntity` 压过 `getEntityByCode`）。
5. **`split("\\R")` 与"数 `\n`"两套换行口径不一致**，文件里只要有一个单独的 `\r` 就错开一格；
   改为读入后先把各种换行统一成 `\n`。

验证：`getEntity` 切片现在带上了 `@PreAuthorize`；文件头切片 809→1603；
残片 svc-sys 145→0、svc-auth 19→0、omspad 272→3。

**仍未根治**：这个问题的答案跨两个类（子类告知继承、父类才有注解），而召回只有 6 个名额、
系统又不建模继承关系，所以能不能答对取决于父类切片有没有撞进名额——实测**一次答对、一次答错**。
建议做一跳继承扩展（按 `extends` 把父类方法切片带进来），已记入 README 已知限制第 14 条与测试文档 5.13。
