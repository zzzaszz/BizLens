## 4. 测试中发现并修复的问题

### 4.1 建/改角色接口把 API Key 密文原样返回（安全）

`AiAgentController` 只在 `/list` 里脱敏，`/create` 与 `/update` 返回的实体带着完整 `ApiKeyEnc`。
虽然是密文，但把库里的密钥材料交给前端不应发生（`AES_KEY` 一旦泄露即可解出明文）。
修复：抽出 `maskApiKey()`，三个出口统一走它。

### 4.2 关闭会话失败时静默返回 false

`closeConversation` 直接把 service 的布尔值返回，会话不存在或不属于自己时返回 `false` 而不报错——
前端把"失败"当成功处理。修复：与 `reopen` 对齐，归属校验不过就抛业务异常。
同时 `/close` 接口补了 try/catch（本类没有全局异常处理器，抛出去会经 `/error` 变成空 body 的 HTTP 500）。

### 4.3 两套时钟导致 `UpdatedAt` 早于 `CreatedAt`

插入会话用的是 JVM 时间（`new Date()`），而 `touch`/`updateStatus` 用的是数据库 `CURRENT_TIMESTAMP`。
本机两者相差约 13 秒，实测出现 `createdAt 11:34:10` 而 `updatedAt 11:33:57`。
会话列表正是按 `UpdatedAt` 倒序，混用两套时钟会让排序不可靠。
修复：更新时间统一由应用传入，与插入保持同一时钟。

### 4.4 流式接口未登录时返回空 body 的 HTTP 500

`AuthAspect` 在鉴权失败时返回 `R.fail(401, ...)`，但 `/ai/chat/stream` 的返回类型是 `SseEmitter`，
Spring 按方法声明类型选返回值处理器 → 类型不匹配 → 空 500，前端只能显示"发送失败：HTTP 500"，
既看不出是登录失效，也无法据此跳登录页。
修复：切面识别返回类型为 `SseEmitter` 的接口，改用带回 `event:error` 的 `SseEmitter` 返回。
前端配套：`AiChat.vue` 识别到"登录已过期"后清理本地登录态并跳登录页（流式请求走原生 fetch，不经过 axios 拦截器）。

### 4.5 续聊失败会让输入框永久禁用（本轮引入的回归）

`sendMsg` 里新增的"先重新打开再发送"写在 `try` 之外，`aiReopenConversation` 被拦截器 reject 时异常
逃出函数，`sending` 停在 `true`，输入框与发送按钮永久禁用，只能刷新页面。
修复：把续聊与发送一起纳入同一个 `try/finally`，并顺带把占位气泡下标提到 `try` 之外（否则 `catch` 里引用不到）。

### 4.6 早期会话给了"能继续"的假承诺

库里 9 条历史会话的 `AgentId` 为 `null`（会话必须绑定角色的规则是后来才加的），
它们既打不开续聊（`reopen` 会以"会话未绑定角色"拒绝），也发不出消息，
但界面提示"发送消息会自动重新打开并继续这段对话"。
修复：区分两种情况——未绑定角色的会话提示"只能查看历史"并禁用输入框；已绑定角色的才提示可续聊。

## 5.2 第三轮：澄清"没配凭据为什么能索引到私有仓库"

起因：发现项目「444」的地址是**私有仓库**，页面上却没有配任何凭据。第一轮曾判断"因为它是公开仓库"，
这个结论被实测证伪。

### 实测过程与结论

| 检查 | 命令 / 方式 | 结果 |
| --- | --- | --- |
| 仓库可见性 | 匿名 GET `api.github.com/repos/zzzaszz/404-forum` | **404 → 私有** |
| 无交互能否读到 | `GIT_TERMINAL_PROMPT=0 git ls-remote <url> HEAD` | 成功，返回 `8788cf1…`，与库里 `git_commit` 完全一致 |
| 凭据来源 | 查 `credential.helper` 与凭据文件 | 全局 `credential.helper=store`，`~/.git-credentials` 中**存在 github.com 条目** |

**结论**：克隆成功不是因为仓库公开，而是因为 `git clone` **静默使用了运行机器上存储的凭据**。
`AiCodeIndexServiceImpl.runGitClone` 确实没有传任何鉴权参数，但 `git` 会自行查找并套用
`credential.helper` / `~/.git-credentials` / SSH key / 系统凭据管理器里的凭据——
"没传参数"与"没用凭据"是两件事。

### 由此暴露的安全问题（未修复，已记入 README 待完成第 1 项）

- 项目接口只校验"项目是不是我创建的"，**不校验"我有没有权限读这个 Git 仓库"**。
  任何注册用户都可以填一个自己无权访问的私有仓库地址，让系统用机器凭据克隆并索引，
  再通过问答获取这份代码的业务信息。这与产品"不向客户泄露源码"的定位直接冲突。
- `credential_ref` 是装饰字段，事后无法审计某次克隆用的是谁的凭据。

### 顺带修正的误导文案

第一轮把该列文案改成了「公开仓库可留空」，这等于在页面上替用户断言"仓库是公开的"——
正是这次被证伪的那个假设。已改为只描述字段本身（「未填写 / 已填写（未生效）」），
并在提示里说明克隆实际用的是运行机器的凭据。

## 5.3 切断环境凭据继承（对应 5.2 的安全问题）

按 5.2 的结论做了修复，并逐条验证。

**改动**：`AiCodeIndexServiceImpl.applyIsolatedGitEnv` —— 每次索引为 git 进程准备一套干净环境：
`HOME`/`USERPROFILE`/`XDG_CONFIG_HOME` → 空的临时目录（用完随工作区一起删）、
`GIT_CONFIG_GLOBAL` → 该目录下不存在的 `.gitconfig`、`GIT_CONFIG_NOSYSTEM=1`、
`GIT_CONFIG_COUNT=1` + `credential.helper=`（空值表示重置 helper 列表）、
`GIT_TERMINAL_PROMPT=0`，并移除 `SSH_AUTH_SOCK` / `GIT_SSH_COMMAND` / `GIT_ASKPASS`。
注意是在 JVM 现有环境之上修改，**不清空环境**（`SystemRoot` 等清掉会让网络都不通）。

| 编号 | 用例 | 期望 | 实测 |
| --- | --- | --- | --- |
| S-01 | 隔离环境下访问**私有**仓库 | 失败，且报错含 `terminal prompts disabled` | 通过：`fatal: could not read Username for 'https://github.com': terminal prompts disabled` |
| S-02 | 隔离环境下访问**公开**仓库 | 成功 | 通过：`7fd1a60b…` |
| S-03 | 应用内：私有仓库项目排队索引 | `FAILED`，原因说明已停用机器凭据 | 通过（`404-forum`：`无法访问该仓库：克隆已停用运行机器的 Git 凭据…`） |
| S-04 | 应用内：公开仓库项目排队索引 | `READY` | 通过（`octocat/Hello-World`：commit `7fd1a60b01f91b314f59955a4e4d4e80d8edf11d`） |

S-01/S-02 是脱离应用、直接对 `git ls-remote` 做的对照，用来确认隔离环境本身的行为，
避免"应用里失败了"这种单一来源的结论。测试用的项目已删除。

**副作用（预期内）**：项目「444」指向私有仓库，重新排队索引会失败；
其切片仍在库中，因此现有对话不受影响。

## 5.8 第八轮：内网 GitLab 克隆报 502（代理继承回归）

用户报告：内网项目 `http://git.inksdev.com/mfomspad/mf-omspad.git` 索引失败，
`fatal: unable to access '...': The requested URL returned error: 502`。

### 定位过程

| 观察 | 结论 |
| --- | --- |
| 502 响应头有 `Proxy-Connection: keep-alive`、无 `Server:`、`Content-Length: 0` | 不是 GitLab 的 nginx 返回的，是链路上的**代理**返回的 |
| `env` 里有 `HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:7890`（Clash） | 机器上确实有代理 |
| 全局 git 配置有 `http.noproxy git.inksdev.com`、`http.http://git.inksdev.com.proxy`（空） | 平时 git 会**绕过**代理访问内网 |
| `curl --noproxy '*'` → `401 Unauthorized` + `Server: nginx` + `WWW-Authenticate: Basic realm="GitLab"` | **GitLab 本身健康**，只是要身份 |
| 隔离环境 + 去掉代理变量 → 内网报 `could not read Username`（401） | 直连正常 |

**根因**：为切断凭据继承，`applyIsolatedGitEnv` 清空了 git 配置（`GIT_CONFIG_GLOBAL` 指向不存在的文件），
把 `http.noproxy` 这条例外一起清掉了，**却保留了 `HTTP_PROXY`/`HTTPS_PROXY` 环境变量**，
于是内网地址被送进 Clash，报 502。这是上一轮凭据隔离引入的回归。

### 修复与验证

改为：**代理同样不继承，由服务端显式声明**。`applyIsolatedGitEnv` 先移除全部继承的代理变量，
再按 `BIZLENS_GIT_PROXY` / `BIZLENS_GIT_NO_PROXY` 注入；两者都不设时直连。

| 编号 | 配置 | 内网 GitLab | github | gitee |
| --- | --- | --- | --- | --- |
| P-1 | 不给任何代理配置（shell 里仍有 Clash 变量） | 报「该仓库需要凭据」（401）✓ **不再 502** | 失败，提示配置 `BIZLENS_GIT_PROXY` | 未测 |
| P-2 | `BIZLENS_GIT_PROXY=127.0.0.1:7890` + `NO_PROXY=git.inksdev.com,192.168.99.92,...` | 报「该仓库需要凭据」✓ | **READY** ✓ | READY（252 文件）✓ |

P-1 证明**应用不再把机器的代理泄漏给 git 子进程**；P-2 证明**内网直连与外网代理可同时成立**。

**使用提示**：只设 `BIZLENS_GIT_PROXY` 而不设 `BIZLENS_GIT_NO_PROXY`，会把内网 Git 也送去代理，
又回到 502——这一点已写进 README 与失败提示文案。

## 5.9 第九轮：索引状态不刷新（页面停在「索引中」）

用户报告：服务端日志已报索引失败，但 `/projects` 页面**仍显示「索引中」**，数据像是停在"上一次排队索引"那一刻。

### 定位

先查库：`omspad` 的 `status = FAILED`、`updated_at` 就是失败落库的时刻——**后端标记完全正确**。
再用全新标签页加载 `/projects`，显示的是「失败 / 仓库或分支不存在」——**新加载也是对的**。

所以既不是后端没落库，也不是接口返回错。真正原因是**页面只在进入时加载一次**：
点完「排队索引」拿到的是 `QUEUED`，之后索引任务在后台跑完或失败，页面再也不会去问，
于是永远停在「索引中」，必须手动刷新才能看到结果。这是纯前端缺陷。

### 修复与验证

`CodeProjects.vue` 增加轮询：只要还有项目处于"正在索引"（复用 `isIndexRunning` 的判定，
含 10 分钟时间窗，避免卡死状态导致永久轮询），每 3 秒静默刷新一次；跑完立刻停。
轮询用 `quiet` 模式不动 loading 态，整表不会每次都闪一下；组件卸载时清掉定时器。

| 编号 | 用例 | 期望 | 实测 |
| --- | --- | --- | --- |
| R-01 | 点「排队索引」后不手动刷新 | 状态自己从 排队中/索引中 走到 已就绪 | 通过：1.5s 显示「索引中」→ 4.5s 显示「已就绪」，全程未刷新 |
| R-02 | 索引中时按钮状态 | 「排队索引」禁用、不能建角色 | 通过 |
| R-03 | 跑完后停止轮询 | 不再有请求 | 通过（状态稳定后不再变化） |

**顺带改进**：分支名写错时报「分支不存在：仓库里没有配置的这个分支……（Git 默认分支可能是 main，也可能是 master）」，
比原始 git 报错更直接——用户这次正是踩在这个上（仓库默认分支是 master，项目里填的 main）。

## 5.10 第十轮：两处资源泄漏

起因：评估"项目越来越多会不会占空间越来越大"。实测发现两处会只增不减，均已修复。

### 泄漏一：索引临时工作区（实测 25 个目录 / 309 MB，最早两周前）

清理代码本来就写在 `finally` 里，但**从来没成功过**。根因不是"没写清理"，而是：

```
Files.deleteIfExists 抛 AccessDeniedException | writable=false |
  .git\objects\pack\pack-xxx.idx / .pack / .rev
```

**git 在 Windows 上会把 `.git/objects/pack` 下的打包文件设成只读**，Java 的
`Files.deleteIfExists` 遇到只读文件直接抛异常（不像 `rm` 会先 chmod），于是目录删不空、
整棵工作区留在临时目录里。

修复：① 删之前先清掉只读属性（`File.setWritable(true)`，Linux 上是空操作）；
② 补上兜底——启动时与每次索引前扫临时目录，清掉超过 1 小时仍未删掉的残留（跳过本进程在用的）。

| 编号 | 用例 | 期望 | 实测 |
| --- | --- | --- | --- |
| M-01 | 修复前启动（含只读文件的残留） | 删不掉 | 14 条 `AccessDeniedException`，只成功 1 个 |
| M-02 | 修复后启动 | 清掉过期残留 | **清理 14 个、释放约 235 MB**，剩余从 26 降到 12 |
| M-03 | 不足 1 小时的目录 | 保留（可能是在跑的任务） | 通过（14:03 之后的都保留） |
| M-04 | **修复后走一次真实索引** | `finally` 里就能删干净 | 通过（索引后目录数不变，无新增残留） |

### 泄漏二：Redis 热上下文永不失效

`setCacheObject(key, cached)` 未设 TTL，每个聊过的会话（最多 50 条消息）永久占内存；
删会话会清，但关闭会话不会。修复：TTL 7 天，写入时续期。

| 编号 | 用例 | 期望 | 实测 |
| --- | --- | --- | --- |
| M-05 | 新写入的热上下文 TTL | 约 604800 秒 | 通过（实测 `604791`，差值即请求耗时） |
| M-06 | 旧数据（旧代码写入） | 仍是 `-1`，需自然淘汰或重启换代 | 通过（读取命中缓存不会续期，符合预期） |

## 5.11 第十一轮：索引一直「索引中」+ 进度可见

用户报告 `omspad` 一直显示「索引中」。

### 定位

| 检查 | 结果 |
| --- | --- |
| 库里状态 | `omspad` = `INDEXING`，`updated_at = 15:00:56`（**6 分钟没动过**） |

| 那次的工作区 | `bizlens-index-44…` 有 `.git`、4.5 MB，最后写入 15:01 —— **半截克隆** |

结论：**服务在索引途中被重启**（用户当时正好在重启以加载代理修复），`finally` 没执行、
状态没回写，于是永远停在「索引中」，而实际什么都没在跑。根因不是"索引太慢"，
而是**进程异常退出后没有任何机制收敛状态**。

### 修复

1. **心跳**：索引运行期间每 30 秒推进一次 `updated_at`，让"还在跑"可判断。
2. **启动收敛**：服务启动时把超过 180 秒没有心跳的 `QUEUED/INDEXING` 置为 `FAILED`，
   原因写明「索引任务被中断：服务在索引途中退出…」；只重置超期未心跳的，避免误伤其它实例。
3. **中断识别**：前端对"状态是索引中但已无心跳"显示**「索引中断」**（灰色标签）而不是「索引中」。

### 进度显示

| 编号 | 场景 | 期望 | 实测 |
| --- | --- | --- | --- |
| N-01 | 启动时收敛中断任务 | 卡住的变成失败并说明原因 | 通过（日志「已把 1 个中断的索引任务置为失败」，`omspad` → `FAILED`） |

| N-03 | 索引中 | 「已用 X 秒，预计还需约 Y」并逐秒递增 | 通过（`已用 0→1→2…` 秒，预测 `5→4→3→2→1` 秒） |

| N-05 | 索引完成 | 显示完成日期时间 | 通过（「已就绪 10-07 15:14 完成」） |
| N-06 | 索引失败/中断 | 显示失败/中断时间 + 可重排 | 通过（「失败 10-07 15:10 失败 索引被中断…重新排队即可」） |

它不反映本次的实际进度（拿不到"解析到第几个文件"），大仓库上只能作为量级参考。

| B-06 | 失败项目 | 单独失败不影响其它项目 | 通过（`444` 因未配访问令牌失败，其余 4 个正常完成） |

**顺带修掉一处前后端口径不一致**：后端的"重排守卫"原本用 10 分钟时间窗，
而心跳机制与前端已改为 180 秒——会出现"前端显示可重新索引、后端却拒绝"。
已把后端常量改为 `STUCK_SECONDS = 180`，与 `AiCodeIndexServiceImpl.HEARTBEAT_GRACE_SECONDS` 对齐，
两处注释都写明了必须一致。

**一个观察（未改）**：项目索引失败时，「索引统计」列显示的仍是**历史上一次成功索引**的文件/切片数，
容易出现"状态是失败、却显示 239 文件"的观感。它是有意的（保留上次成功的成果信息），
但需要在状态列看到失败原因才不会误解。

## 5.13 第十三轮：AI 答错「SYSM03B4/getEntity 的接口权限」的排查

用户反馈：问 `/system/SYSM03B4/getEntity` 的接口权限与调用方式，AI 回答"片段里找不到这个接口、
无法确认权限"，但该接口确实存在且有 `@PreAuthorize(hasPermi = "PiPermission.List")`。

### 逐个查出来的缺陷（共 5 个，均已修）

| # | 缺陷 | 证据 | 影响 |
| --- | --- | --- | --- |
| 1 | **方法切片的行区间不含上方注解**。`collectMethods` 用 `lineOf(matcher.start())` 当起点，而正则从 `public` 起匹配，上面几行注解全被丢掉 | `PipermissionController.getEntity` 的切片从 `public R<...> getEntity` 开始，**没有 `@PreAuthorize`** | 「这个接口要什么权限」这类问题**永远查不到答案** |
| 2 | **FILE 级切片只取 800 字符** | `SYSM03B4Controller.java`（50 行）的文件头切片停在 `@ApiOperati`，正好切在第一个方法之前 | 模型只能回答"片段在方法注解处就被截断了，看不到挂了哪些方法" |
| 3 | **`^\s*` 会吃进前一行的空行**，导致记录的行号落在空行上，取出的片段只有一个换行符 | svc-sys 里有 **145 个**长度≤4（首字符就是换行）的 MAPPER 残片 | 残片长度最短，在按长度升序的排序里排最前，**占满召回名额** |
| 4 | **召回排序 `length(source_snippet) ASC`** 把最短（往往最没用）的排前面 | 上述残片全部排在第 1-9 位，真正的目标切片排在第 30 位之后 | 6 个名额被垃圾占满 |
| 5 | **`split("\\R")` 与"数 `\n`"两套换行口径不一致**。文件里只要有非 `\n` 的换行符（如单独的 `\r`），两套编号就错开一格 | `AiChatMessageMapper.xml` 第 13 行是空行、第 14 行才是 `<insert`，切片却记 `startLine=13` | 残留 51 个同类残片 |

### 修复与验证

1. 提取方法时**向上把相邻的注解/注释行纳入切片**（遇空行继续、遇代码行停止）；
2. FILE 头 800 → **2400** 字符（实测 809 → 1603，能覆盖到类声明与后续方法）；
3. 四个正则的行首 `^\s*` → `^[ \t]*`，不再跨行；
4. 排序改 `score DESC, length DESC`，并加**精确同名加成**（`getEntity` 压过 `getEntityByCode`）；
5. 读文件后**先把各种换行统一成 `\n`**。

| 编号 | 用例 | 结果 |
| --- | --- | --- |
| X-01 | `PipermissionController.getEntity` 切片是否含注解 | 通过：切片现在以 `*/ @ApiOperation… @RequestMapping… @PreAuthorize(hasPermi = "PiPermission.List") public … getEntity` 开头 |
| X-02 | FILE 头切片长度 | 通过：809 → 1603 |
| X-03 | 残片数（svc-sys） | 通过：145 → 51 → **0** |
| X-04 | 残片数（其余可重排的项目） | 通过：svc-auth 19 → 0、开源1 0、omspad 272 → 3 |
| X-05 | **端到端：同样的提问** | **一次答对**（明确给出 `PiPermission.List`、租户隔离、GET 调用方式、入参主键），**另一次仍答错** |

### 尚未根治的部分（X-05 的两次结果不一致）

这个问题的答案**跨两个类**：子类 `SYSM03B4Controller` 只告知"继承自 `PipermissionController`"，
注解在父类的 `getEntity` 上。要答对，6 个召回名额里必须同时出现**子类的文件切片**和**父类的方法切片**。

现在系统**不建模继承关系**（Code Graph 仍是 README 里的待办），只能靠关键词撞运气：
父类切片撞进来就答对，撞不进来就答错。两次提问的结果不同正说明这一点。

已做的缓解只是"让结果可复现"（加了 `c.id` 兜底排序），**并没有消除这个不确定性**。
真正的修法两条：① 召回时做**一跳继承扩展**（命中某类的文件切片时，顺着 `extends X`
把同项目里 `X.java` 的方法切片也带进来）；② 向量化语义召回（README 既有待办）。
① 改动可控、针对性强，建议优先。

## 6. 仍未覆盖 / 已知遗留

1. **流式对话是"尽早断"而不是"事前拦"**。打字机效果下内容会开始外送，`AiSafetyGuard`
   只能在判到的那一刻中断；已推送的部分靠 `reset` 纠正。要求"一个字符都不外泄"时应改回整段发送。
2. **索引卡死判定是启发式的 10 分钟时间窗**。真有任务跑超过 10 分钟时，界面会误放开「重新索引」，
   点了就会并发两个索引互相覆盖。根治要引入任务心跳或超时字段。
3. **索引进度不可见**：状态机只有 `PENDING/QUEUED/INDEXING/READY/FAILED`，没有中间进度上报。
4. **列表接口仍全量返回**（会话、项目、角色），未分页。
5. **SSH 地址不支持**（HTTPS + 令牌已支持）。隔离环境不继承 `~/.ssh`，也未支持部署密钥。
6. 自建 GitLab 只用了一个**不可达**的域名验证"地址不被拦截"，**没有对真实的自建 GitLab 实例做过端到端克隆**
   ——本机网络到 `192.168.99.92`、`git.inksdev.com` 均不通。
6. **前端无自动化测试**，本轮全部为人工驱动的端到端验证；`pnpm run test` 的 Vitest 兼容问题仍在。
7. 未验证多用户场景（越权访问他人会话/项目/角色只做了代码路径审查，未构造第二个账号实测）。
8. 未验证的接口分支：`openai` / `qwen` / `custom` 三个 Provider 的模型列表与对话（沿用 README 原有记录）。

# 后端构建
