# BizLens 个人知识库接入方案

> **目标**：在现有 BizLens AI 代码问答之上接入个人知识库（Git 托管的 Markdown），与代码知识库共用同一套混合检索（Hybrid RAG）与上下文构建链路。
>
> **原则**：优先在现有 BizLens AI 架构上扩展，**不另起一套 Obsidian → Qdrant 系统**；保留现有关键词检索，以最小改动方式逐步升级为统一 Hybrid RAG。
>
> **基线**：本方案基于 2026-10-08 的代码现状编写，涉及的表结构、类名、常量均对应当前仓库。

> **实现状态**：Git Markdown 个人知识库的建库、索引、角色关联和统一对话召回已实现。当前实现支持
> HTTPS Git、Markdown 标题切片、checksum 增量索引、敏感信息脱敏、可选 embedding/pgvector 和索引进度；
> PDF/Wiki/Notion/Web、SSH、文档预览和跨来源 RRF 统一排序仍属于后续优化。

## 0. 现状基线（改造起点）

### 0.1 已有能力一览

| 环节 | 现状 | 位置 |
| --- | --- | --- |
| 代码项目元数据 | `ai_code_project`（Git 地址、分支、Commit、凭据、索引状态、进度、耗时） | `db/schema-postgresql.sql` |
| 代码文档 | `ai_code_document`（path / language / checksum / 行号），`UNIQUE(project_id, path, checksum)` | 同上 |

| 对话与流式 | `AiServiceImpl` + SSE（`delta` / `reset` / `error` / `done`）+ Redis 热上下文 | `AiServiceImpl`、`AiChatController` |
| 安全 | Prompt 注入检测、输出拦截 `AiSafetyGuard`、审计 `ai_security_audit` | `ai/AiSafetyGuard.java` |
| 前端 | 工作台 / 业务问答 / AI 角色 / 代码项目 / 个人知识库五个页面，API 集中在 `web/src/api/index.js` | `web/src/views` |

### 0.2 五条关键结论（决定了方案怎么改）

1. **`ai_code_chunk.embedding` 列已存在，但是 `JSONB` 类型且从未写入。** 原第 1 条"AiCodeChunk 增加 embedding"实际是**类型迁移**（JSONB → `vector`，或新加一列），不是新增列。迁移必须保留旧列直到回填完成。
2. **现有 Git 索引能力可直接复用**：克隆隔离、凭据注入、心跳、中断收敛、工作区清理这套逻辑与"索引什么语言"无关，知识库不需要重写。
3. **角色与来源已是多对多**，知识库只需照 `ai_agent_project` 的形状再加一张关联表，模型层不需要重构。
4. **向量能力是可选增强**：代码和个人知识库均可接入 OpenAI-compatible embedding 与 pgvector；未配置或扩展不可用时自动退回关键词召回。
5. **关键词召回不能删**：表名、类名、专有术语这类精确匹配恰好是 `ILIKE` 更强的地方，向量召回解决的是注释型业务术语（README 已知限制 1）。

## 2. 关键设计决策

### 2.1 为什么扩展现有架构而不另建 Obsidian → Qdrant

| 维度 | 另建 Obsidian → Qdrant | 扩展现有架构（本方案） |
| --- | --- | --- |
| 索引器 | 新写一套文件监听 + 同步 | 复用 Git 克隆隔离、凭据、心跳、中断收敛 |
| 存储 | 两套库、两份元数据 | 同一个 PostgreSQL，向量用 pgvector |
| 检索 | 两套召回、两套排序 | 一个 `AiRetrievalService` 统一融合 |
| 角色/权限 | 需要重新建关联与越权校验 | 复用 `created_by` 归属 + 多对多关联模式 |
| 运维 | 多一个中间件 | 只需给现有库装一个扩展 |

结论：知识库是"另一种切片来源"，不是"另一套系统"。

### 2.2 知识源抽象：与代码项目并列，不做合并

原方案要求"统一设计为 `KnowledgeSource`，不要绑定为 `ObsidianSource`"——本方案落实为：**表名 `ai_knowledge_source` + `source_type` 字段**，本期只实现 `GIT_MARKDOWN`，为 `PDF` / `WIKI` / `NOTION` / `WEB` 预留取值。

但**不建议**把 `ai_code_project` 也改造成 `ai_knowledge_source` 的一种（即"全部来源统一成一张表"）：

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| A（**推荐**） | 保留 `ai_code_project`，新增平行的 `ai_knowledge_source`，角色分别关联两张关联表 | 两张表字段有部分重复；召回层做融合 |
| B | 代码项目降级为 `source_type='GIT_CODE'` 的一种来源 | 需改动索引器、5 个接口、前端 2 个页面、`ai_code_document/chunk/relation` 三张表的外键，且 `ai_code_*` 大量 SQL 要重写 |

代码侧已经有 `ai_code_document` / `ai_code_chunk` / `ai_code_relation` 三张表挂在 `ai_code_project` 上，走路线 B 等于一次全量重构。**选 A**：重复的是几个元数据字段，换来的是零破坏。

### 2.3 Embedding 提供方与维度（前置阻塞项，未确认前无法开工）

方案原文写的是 `VECTOR(1536)`，但 1536 维对应的是 OpenAI `text-embedding-3-small`，而现有 Provider 只有 DeepSeek。**DeepSeek 平台当前提供的是 chat / models 接口，未见 embeddings 接口**，因此向量化大概率需要单列一个 embedding 提供方。

需要先确认并定死三件事：

| 待定项 | 候选 | 影响 |
| --- | --- | --- |
| 提供方 | OpenAI 兼容网关 / 本地部署（bge-m3 等）/ 云厂商 embedding 服务 | 决定是否需要新依赖与网络策略（内网 Git 需走 `BIZLENS_GIT_NO_PROXY`，embedding 出网则需 `BIZLENS_GIT_PROXY` 同类配置） |
| 模型 | 与提供方绑定 | 决定维度 |
| 维度 | 1536（text-embedding-3-small）/ 1024（bge-m3、通义 v3）/ 768 | **建表即固定，改维度＝重建列 + 重跑全部向量，不可逆** |

实现上抽象为 `AiEmbeddingProvider`（接口 + OpenAI 兼容实现，即 `POST {base-url}/embeddings`），配置沿用现有 `ai.deepseek.*` 的写法：

```yaml
ai:
  embedding:
    provider: ${AI_EMBEDDING_PROVIDER:openai-compatible}
    base-url: ${AI_EMBEDDING_BASE_URL:}
    api-key: ${AI_EMBEDDING_API_KEY:}
    model: ${AI_EMBEDDING_MODEL:text-embedding-3-small}
    # 必须与建表脚本里的 vector(N) 一致：不一致时 pgvector 插入会直接报错（天然校验）
    dimension: ${AI_EMBEDDING_DIM:1536}
    batch-size: ${AI_EMBEDDING_BATCH:32}
    timeout-ms: ${AI_EMBEDDING_TIMEOUT_MS:30000}
```

> 注意：embedding Key 与对话 Key 分开配置。给角色配的存储 Key（`"AiAgent"."ApiKeyEnc"`）是**对话用**的，不要拿来算向量——两者的计费主体和可用模型是两回事。

### 2.4 Markdown 分块策略

分块质量直接决定召回质量，比选哪个模型更值得花时间。

| 规则 | 取值/做法 | 理由 |
| --- | --- | --- |
| 主边界 | Markdown 标题层级（H1~H3） | 天然语义边界，且能还原"这段属于哪个主题" |
| 标题路径 | `heading_path` 记 `一级/二级/三级` | 单块脱离上下文后仍可判断归属，也便于回答里引用 |
| 目标长度 | 300~800 中文字符 | 太碎会稀释召回，太长会挤占 prompt |
| 硬上限 | `MAX_KNOWLEDGE_CHUNK_CHARS`（建议 1500） | 与代码侧 `MAX_SNIPPET_IN_PROMPT = 1500` 对齐，便于统一预算 |
| 超长小节 | 按空行段落切；段落仍超长再按字符硬切，保留 ~100 字符 `overlap` | 避免一句话被切断而语义断裂 |
| 不可分割单元 | 代码块（```）、表格、有序列表整体成块，仅在超硬上限时才切并标 `truncated` | 切碎代码块和表格会让内容失去意义 |
| 短小节 | 小于阈值的相邻同级小节合并 | 避免产生大量只有一两行的碎片块 |
| 元数据 | `metadata` 记 `headingPath` / `headingLevel` / `startLine` / `endLine` / `charCount` / `chunkIndex` | 与代码侧 `metadata->>'startLine'` 的口径保持一致 |
| 脱敏 | 复用代码索引的敏感词扫描（`password` / `token` / `apiKey` / `privateKey`） | 个人知识库同样可能有随手记的密钥 |

### 2.5 混合检索的融合方式：RRF，而不是加权分数

关键词召回的 score 是 5/2/1 的**人工伪分**，向量召回是 **cosine 距离**——两者量纲不同，直接加权求和等于用一个随手定的系数去平衡两个不可比的数字，调参会变成玄学。

改用 **RRF（Reciprocal Rank Fusion）**，只用排名、不用原始分：

```text
score(d) = Σ_i  w_i / (k + rank_i(d))        k = 60（经验值，可配）
```

- 只在某一榜出现的文档，只累加该榜的贡献，不会因为"另一榜没召回"而被惩罚成 0 分。
- 权重 `w_i` 默认两路 1:1，需要偏向精确匹配时再单独调。
- 实现上就是对两路结果各排一次名，再按 `chunkId` 合并累加——不需要新的排序框架。

## 3. 数据模型

### 3.1 新增四张表

> 命名跟随现有约定：表 `ai_knowledge_*`（snake_case），实体 `AiKnowledgeXxxEntity`，Mapper `AiKnowledgeXxxMapper`。
> 脚本建议拆两个文件：`migration-20261008-knowledge.sql`（建表）、`migration-20261008-pgvector.sql`（扩展与向量列）。

```sql
-- pgvector 扩展。需要超级用户或已授权的角色，装不上就整条链路走不通，属阶段 0 前置项。
CREATE EXTENSION IF NOT EXISTS vector;

-- 知识源：本期只有 GIT_MARKDOWN，source_type 为后续 PDF / Wiki / Notion / Web 预留。
CREATE TABLE IF NOT EXISTS ai_knowledge_source (
    id                     BIGINT PRIMARY KEY,
    name                   VARCHAR(128) NOT NULL,
    source_type            VARCHAR(32)  NOT NULL DEFAULT 'GIT_MARKDOWN',
    git_url                VARCHAR(512) NOT NULL,
    git_branch             VARCHAR(128) NOT NULL DEFAULT 'main',
    git_commit             VARCHAR(64),
    -- 仓库内相对子目录，只索引该目录下的 Markdown；空串表示整库
    root_path              VARCHAR(256) NOT NULL DEFAULT '',
    -- 私有知识库凭据，与 ai_code_project 同机制（AES 加密 + credential.helper 注入）
    credential_enc         VARCHAR(512),
    credential_user        VARCHAR(128),
    status                 VARCHAR(32)  NOT NULL DEFAULT 'PENDING',
    last_error             TEXT,
    last_indexed_at        TIMESTAMP,
    last_index_ms          BIGINT,
    index_total_files      INTEGER NOT NULL DEFAULT 0,
    index_processed_files  INTEGER NOT NULL DEFAULT 0,
    index_skipped_files    INTEGER NOT NULL DEFAULT 0,
    created_by             BIGINT REFERENCES "User" (id) ON DELETE SET NULL,
    created_at             TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at             TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_knowledge_source_status ON ai_knowledge_source (status, updated_at DESC);
CREATE INDEX IF NOT EXISTS idx_knowledge_source_user   ON ai_knowledge_source (created_by);

-- 文档：按 path 唯一（增量时同路径覆盖）。
-- 注意与 ai_code_document 的 UNIQUE(project_id, path, checksum) 不同：
-- 代码侧靠 checksum 保留多版本，知识库只需要"最新一版 + 判断是否变了"。
CREATE TABLE IF NOT EXISTS ai_knowledge_document (
    id          BIGINT PRIMARY KEY,
    source_id   BIGINT NOT NULL REFERENCES ai_knowledge_source (id) ON DELETE CASCADE,
    path        VARCHAR(1024) NOT NULL,
    title       VARCHAR(512),
    checksum    VARCHAR(128) NOT NULL,
    size_bytes  INTEGER NOT NULL DEFAULT 0,
    chunk_count INTEGER NOT NULL DEFAULT 0,
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (source_id, path)
);
CREATE INDEX IF NOT EXISTS idx_knowledge_document_source ON ai_knowledge_document (source_id);

-- 切片：content 为正文，embedding 维度必须与 ai.embedding.dimension 一致
CREATE TABLE IF NOT EXISTS ai_knowledge_chunk (
    id            BIGINT PRIMARY KEY,
    document_id   BIGINT NOT NULL REFERENCES ai_knowledge_document (id) ON DELETE CASCADE,
    chunk_index   INTEGER NOT NULL,
    heading_path  VARCHAR(512),
    heading_level SMALLINT,
    content       TEXT NOT NULL,
    embedding     VECTOR(1536),
    metadata      JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_knowledge_chunk_document ON ai_knowledge_chunk (document_id, chunk_index);

-- 角色 ↔ 知识库 关联表：形状与 ai_agent_project 完全一致
CREATE TABLE IF NOT EXISTS ai_agent_knowledge (
    agent_id     BIGINT NOT NULL,
    knowledge_id BIGINT NOT NULL,
    created_at   TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_ai_agent_knowledge PRIMARY KEY (agent_id, knowledge_id),
    CONSTRAINT fk_aak_agent     FOREIGN KEY (agent_id)     REFERENCES "AiAgent" ("Id")      ON DELETE CASCADE,
    CONSTRAINT fk_aak_knowledge FOREIGN KEY (knowledge_id) REFERENCES ai_knowledge_source (id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_aak_knowledge ON ai_agent_knowledge (knowledge_id);
```

### 3.2 代码侧 embedding 列迁移（`migration-20261008-pgvector.sql`）

```sql
CREATE EXTENSION IF NOT EXISTS vector;

-- 新列，不动旧的 JSONB embedding，避免不可逆。
ALTER TABLE ai_code_chunk ADD COLUMN IF NOT EXISTS embedding_vec VECTOR(1536);

-- 索引：数据量小（万级切片以内）时可以先不建，等量上来再建。
-- HNSW 建索引期间内存占用较高，maintenance_work_mem 不足会失败。
CREATE INDEX IF NOT EXISTS idx_code_chunk_embedding
    ON ai_code_chunk USING hnsw (embedding_vec vector_cosine_ops);
```

**旧 `embedding`（JSONB）的处置**：本次只加列不删列。确认全量回填完成、且新链路稳定运行一段时间后，再单独出一个 `DROP COLUMN` 的迁移。**不要在同一次迁移里既建新列又删旧列**——回填失败就没有退路了。

> 补充：`ai_knowledge_chunk.embedding` 可直接建成 `VECTOR(N)`，不必像代码侧那样先 JSONB 再迁移——代码侧那个 JSONB 列是早期占位，从未写入过。

## 4. 索引流程（Git Markdown Indexer）

### 4.1 主流程

```text
排队(PENDING→QUEUED) → 拉取(INDEXING) → 逐文档处理 → 批量向量化 → READY
                                              │
                                              └── 失败 → FAILED（写 last_error）
```

1. **前置校验**：知识源归当前用户；地址为 HTTPS（SSH 与代码侧一样不支持，失败原因直接说明）。
2. **克隆/拉取**：复用 `AiCodeIndexServiceImpl` 的隔离 Git 环境（`applyIsolatedGitEnv`：清空继承凭据、按源注入令牌、代理显式配置）。工作区名前缀沿用 `bizlens-index-`，即可被现有 `cleanStaleWorkspaces()` 一并回收。
3. **增量判断**：`git rev-parse` 与 `git_commit` 相同 **且状态为 READY** → 直接跳过，不扫描不向量化（省下的主要是 embedding 费用）。
4. **遍历 Markdown**：限定扩展名 `.md` / `.markdown`；跳过 `node_modules`、`.git`、`.obsidian`、附件目录；单文件大小上限与代码侧分开配置（见 8. 未决项 6）。
5. **逐文档比对**：`sha256(内容)` 与 `ai_knowledge_document.checksum` 一致 → 该文档整篇跳过（**不重新 embedding**）。
6. **重建切片**：变更/新增文档先 `DELETE FROM ai_knowledge_chunk WHERE document_id = ?` 再写新块（外键 `ON DELETE CASCADE` 保证不残留）；仓库里已删除的文件，删除对应 `document` 行。
7. **批量向量化**：按 `batch-size`（默认 32）调用 embedding，失败重试 3 次指数退避；**单批失败只标该文档失败，不整库回滚**。
8. **提交粒度**：按文档提交，而不是整库一个事务——一次索引几百个文件，整库回滚意味着前面几分钟白跑。
9. **收尾**：写回 `git_commit`、`last_indexed_at`、`last_index_ms`；`finally` 删除临时工作区（删前先清只读属性，这是代码侧踩过的坑）。

### 4.2 状态机与进度：完全复用，不新造

`PENDING → QUEUED → INDEXING → READY / FAILED`，心跳 30 秒（`HEARTBEAT_SECONDS`）、宽限 180 秒（`HEARTBEAT_GRACE_SECONDS`）、启动时 `resetStuckIndexing` 收敛中断任务、`last_index_ms` 用于估算剩余时间——这些代码侧已经验过一轮，知识库照用即可，**唯一需要改的是把 project 换成 knowledge source**（建议把 `@PostConstruct` 收敛逻辑写成对两张表各跑一次，而不是复制一份 Service）。

## 5. 统一检索服务

### 5.1 目标接口

```java
public interface AiRetrievalService {
    /** 在角色的全部关联来源（代码项目 + 知识库）内做统一混合检索。 */
    RetrievalResult retrieve(RetrievalRequest request);
}
```

`RetrievalRequest`：`projectIds` / `knowledgeIds` / `question` / 角色模型与 Key（供问题改写用）。

`RetrievalResult.item` 的统一字段：

| 字段 | 说明 |
| --- | --- |
| `sourceType` | `CODE` / `KNOWLEDGE` |
| `sourceId` / `sourceName` | 命中的项目或知识库 |
| `documentId` / `chunkId` | 去重与调试用 |
| `path` / `fileName` | 文件路径 |
| `symbolName` / `chunkType` | 代码侧字段，知识库为空 |
| `headingPath` | 知识库侧字段，代码为空 |
| `content` | 正文/源码片段 |
| `score` / `rank` | 融合后的分数与名次 |
| `retrievalType` | `KEYWORD` / `VECTOR` / `HYBRID`（用于调参与审计） |

### 5.2 向量召回 SQL（知识库侧）

```sql
SELECT kc.id, kd.path, kd.title, kc.heading_path, kc.content,
       1 - (kc.embedding <=> #{vector}::vector) AS similarity
FROM ai_knowledge_chunk kc
JOIN ai_knowledge_document kd ON kd.id = kc.document_id
WHERE kd.source_id IN (...)
ORDER BY kc.embedding <=> #{vector}::vector
LIMIT #{limit}
```

代码侧同理打在 `ai_code_chunk.embedding_vec` 上。两边都**必须限定来源范围**（`source_id IN (...)` / `project_id IN (...)`），否则会跨用户召回。

### 5.3 融合与上下文构建

- 两路各取 topN（`AI_RAG_TOP_K_CODE` / `AI_RAG_TOP_K_KNOWLEDGE`，建议各 6~10），按 2.5 的 RRF 融合，取最终 topN。
- 从 `AiCodeRetrievalService.buildContext` 抽出 `AiContextBuilder`，入参改为统一 hits，**按来源分区**输出：

```text
【代码片段】—— 来自代码项目：inks-service-pms
--- .../OrderServiceImpl.java [METHOD closeOrder] 第 120-180 行 ---
...

【知识库片段】—— 来自知识库：个人Java知识库
--- PostgreSQL/索引优化 第 12-40 行 ---
...
```

- 沿用现有使用约束文案（只解释业务规则、不复述源码、片段不足时如实说明、无命中时注入"本轮未检索到片段"）。
- 代码侧现有的一跳继承扩展、调用链扩展、文件级完整检索**保持不变**，只在融合阶段与知识库结果一起排序。
- 总字符预算：代码侧现有 `MAX_TOTAL_CHARS = 8000`。知识库建议单独给一份预算（如 3000），合起来上限需要**实测 token 成本后再定**，不要拍脑袋抬到很大。

## 6. AI Role 关联知识库

在现有"角色 ↔ 代码项目 多对多"之上，增加"角色 ↔ 知识库 多对多"。

```text
Java开发助手
├── 代码项目：404-forum
├── 代码项目：BizLens
└── 知识库：个人Java知识库
```

| 规则 | 做法 |
| --- | --- |
| 关联入参 | `AiAgentRequest` 增加 `knowledgeIds`（与 `projectIds` 并列，**编辑时整体替换**） |
| 非空校验 | 至少要关联一个代码项目**或**一个知识库；两者皆空时角色没有任何上下文来源，直接拒绝 |
| READY 校验 | 关联的知识库也必须**全部 READY**（沿用"只索引好一半会给出只有一半依据的结论"的既有判断） |
| 归属校验 | 知识库必须归当前用户 |
| 删除语义 | 删知识库通过外键解除关联、不删角色（与删代码项目一致） |
| 错误文案 | `ensureChatReady` 的"角色未关联代码项目"改为"角色未关联任何知识来源" |
| 召回范围 | 对话时在角色的**全部关联项目 + 全部关联知识库**内分别召回，再按来源分区注入同一轮上下文 |

## 9. 实施顺序与验收标准

每个阶段的验收都要能"跑一次看到结果"，不接受"代码写完就算完成"。

### 阶段 0：前置（阻塞全部后续）

| 步骤 | 内容 | 验收 |
| --- | --- | --- |
| 0.1 | 确认 embedding 提供方、模型、维度 | 三方确认记录写进本节 |
| 0.2 | 安装 pgvector | `SELECT extversion FROM pg_extension WHERE extname = 'vector';` 有值 |
| 0.3 | 确认知识库实际 Git 地址、分支、是否私有 | 能匿名或带令牌 `git ls-remote` 成功 |

> 本机无 `psql`（`Program Files` 下也没有），库上验证用 JDBC 探针执行只读查询，不要靠"SQL 看着没问题"下结论。

### 阶段 1：代码侧向量化

1. `AiEmbeddingProvider` 接口 + OpenAI 兼容实现 + 配置项。
2. `migration-20261008-pgvector.sql`：加 `embedding_vec` 列。
3. 索引流程末尾批量生成向量。

**验收**：随机抽 10 条切片 `embedding_vec IS NOT NULL`；构造语义相近但用词不同的两句中文，相似度明显高于不相关句子。

### 阶段 2：代码侧混合检索

1. `AiCodeChunkMapper` 增加 `searchByVector`。
2. `AiCodeRetrievalService` 改为关键词 + 向量两路，RRF 融合。

**验收**：用 `// 订单超过 30 分钟未支付自动关单` 这类"只出现在注释里"的业务术语提问，能召回此前关键词召不到的切片（对应 README 已知限制 1）。

### 阶段 3：知识库数据模型 + 索引器

1. `migration-20261008-knowledge.sql` 四张表。
2. 复用 Git 克隆隔离/凭据/心跳/中断收敛，实现知识库索引器。
3. 遍历 + `ai_knowledge_document` 落库 + 按 checksum 增量。

**验收**：个人知识库索引到 `READY`；`SELECT count(*) FROM ai_knowledge_document WHERE source_id = ?` 与仓库内 `.md` 文件数一致；重复排队索引时确认文档走了"跳过"分支（日志可见）。

### 阶段 4：Markdown 分块 + 向量化

**验收**：抽一个多级标题文档，检查 chunk 的 `heading_path` 与原文层级一致；每块 `content` 非空、无被切断的代码块与表格；`embedding` 非空；相邻短小节已合并。

### 阶段 5：统一检索与上下文

1. `AiRetrievalService` + 统一 `RetrievalHit`。
2. `AiContextBuilder` 按来源分区。
3. `AiServiceImpl` 的注入点从 `AiCodeRetrievalService` 换到新服务。

**验收**：服务端日志能看到两路各自召回条数与融合后的 topN；注入的上下文里两个来源都出现过。

### 阶段 6：AI Role 关联知识库

后端关联表 + 校验 + 前端多选。

**验收**：一个角色同时关联 1 个代码项目 + 1 个知识库，提问能同时引用两边内容；把知识库状态改为非 READY 后，建角色/建会话被正确拒绝。

### 阶段 7：端到端与收尾

1. `ai_security_audit.retrieval_meta` 补记来源类型与命中来源（便于复盘"为什么这次答偏了"）。
2. 同步 README 开发进度、开发文档、开发日志、测试文档。

**验收**：完整走通「注册 → 建代码项目 → 建知识库 → 分别索引 → 建角色（关联两者）→ 对话 → 追问」，全程无空 body 的 500。

## 11. 风险与未决项

1. **embedding 提供方与维度未定 —— 唯一的硬阻塞**。DeepSeek 当前未见 embeddings 接口，若确认没有，就必须引入第二个提供方。维度一旦建表就不可改（改维度＝重建列 + 重跑全部向量），必须在阶段 0 定死。
2. **pgvector 安装权限未知**。`CREATE EXTENSION` 需要超级用户或预授权角色，生产库（`192.168.99.240:55432`）上能否执行需先确认。
3. **向量化成本未估**。全量重跑代码库（参考：404-forum 239 文件 / 1410 切片）与个人知识库的 embedding 费用、耗时需要小范围实测后再决定是否分批/限速。
4. **旧 `embedding`（JSONB）列的清理**属不可逆操作，必须在回填验证通过后单独一次迁移执行。
5. **知识库的单文件上限**尚未定。代码侧默认 `AI_INDEX_MAX_FILE_BYTES = 2097152`、`AI_INDEX_MAX_FILES = 2000` 是为源码设的且可配置；个人知识库若含长文或大量笔记，需要独立配置，并明确"跳过了多少个文件"要在页面上可见。
6. **中文关键词召回弱**的问题在知识库侧同样存在，向量召回是主要收益点；但**不要因此删掉关键词召回**——专有名词（表名、类名）恰恰是关键词更强的地方。
7. **知识库仓库信息未确认**：实际 Git 地址、分支、是否为私有（是否需要配令牌）目前只是"个人知识库本身已经是 Git 项目并部署"这一句描述，开工前需落到具体仓库。
8. **增量依赖 Git 提交**。若知识库是本地 Obsidian vault 未推送，增量判断会失效——需要先确定同步机制（定时推送 / 手动推送）。
9. **Rerank 本期不做**。当前架构下引入 cross-encoder 需要新增模型依赖与一次额外推理延迟，先靠 RRF + 少量调参验证效果，不够再上。
10. **来源扩展只留字段不留实现**。`source_type` 允许 `PDF` / `WIKI` / `NOTION` / `WEB`，但本轮不实现正文抽取，避免范围蔓延成"通用知识库平台"。
