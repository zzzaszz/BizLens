# BizLens AI 登录安全增强方案

> 2026-10-10 立项。三个目标：**邀请码注册**、**密码错误累计**、**连续失败 5 次出验证码**。
> 现有登录框架（JWT 双 Token + Redis 校验 + `JwtFilter`/`AuthAspect` 双白名单）**保持不变**，
> 全部改动都是在既有登录链路上做"前置校验 + 旁路接口"。

## 1. 现状梳理（方案依据）

登录链路：`AuthController` → `AuthServiceImpl.login/register` → `issueTokens` 签发双 Token 写 Redis；
`JwtFilter` 解析 Token 填 `UserContext`，`AuthAspect` 对 controller 包全部接口统一校验，
免登录路径靠**两处** `SKIP_PATHS` 白名单（`JwtFilter.java:24`、`AuthAspect.java:43`）。

已有防护（全部保留，本方案不重复建设）：

| 防护 | 现状 | 位置 |
| --- | --- | --- |
| IP 登录限流 | 同 IP 每分钟 10 次 | `AuthServiceImpl` `LOGIN_MAX_TIMES` |
| IP 注册限流 | 同 IP 每天 5 个账号 | `AuthServiceImpl` `IP_MAX_REGISTER` |
| 账号枚举防护 | 账号不存在与密码错误统一提示"账号或密码错误" | `AuthServiceImpl.login` |
| 注册格式校验 | 账号 3-32 位字母数字下划线、密码 6-32 位 | `USERNAME_PATTERN` |
| ID 生成 | `SnowflakeIdGenerator` | 已有 Bean |

关键约束：`R` 支持 `R.info(code, msg, data)` 自定义业务码（`R.java:50`）；
前端 `request.js` 响应拦截器对非 200 只 `reject(new Error(res.msg))`，**会丢掉 code 和 data**，方案 5.4 有对应小改。

## 2. 总体设计

```text
注册（改动）                          登录（改动）
──────────────                       ──────────────
输入账号/密码/邀请码                   输入账号/密码 [ + 验证码 ]
      │                                     │
      ▼                                     ▼
校验邀请码存在、未用、未过期            读 login:fail:<username>
      │                                     │
      ▼                                     ▼
条件 UPDATE 占用码（防并发）      failCount ≥ 5 → 强制校验图形验证码
      │                                     │
      ▼                                     ▼
事务内插入 "User"                 密码错误 → INCR 计数（续期 30 天）
      │                                     │
      ▼                                     ▼
签发 Token（不变）                密码正确 → DEL 计数（清零）→ 签发 Token（不变）
```

新增/改动清单：

| 层 | 内容 | 类型 |
| --- | --- | --- |
| 数据库 | 新表 `ai_invite_code` + 迁移脚本 | 新增 |
| 后端 | 邀请码 `InviteCodeController/Service/Mapper/Entity` | 新增 |
| 后端 | `GET /api/auth/captcha` 图形验证码 | 新增 |
| 后端 | `AuthServiceImpl` 登录/注册流程插入校验步骤 | 修改 |
| 后端 | `LoginRequest`/`RegisterRequest` 加字段 | 修改 |
| 前端 | `Login.vue` 邀请码输入、验证码行；邀请码管理弹窗 | 修改 |
| 前端 | `request.js` reject 时携带 code/data（约 2 行） | 修改 |

明确不做（边界）：不锁定账号、不引入短信/邮件通道、不改 Token 机制、不加定时任务、
`"User"` 表不加列（失败计数放 Redis，邀请关系由 `ai_invite_code.UsedBy` 追溯）。

## 3. 邀请码注册

### 3.1 表结构

追加 `svc/src/main/resources/db/migration-20261010-invite-code.sql`（`CREATE TABLE IF NOT EXISTS`，可重复执行）：

```sql
CREATE TABLE IF NOT EXISTS ai_invite_code (
    id          BIGINT PRIMARY KEY,                 -- SnowflakeIdGenerator
    code        VARCHAR(16) NOT NULL,               -- 8 位大写字母数字（去混淆字符）
    created_by  BIGINT NOT NULL REFERENCES "User" ("Id") ON DELETE CASCADE,
    used_by     BIGINT REFERENCES "User" ("Id") ON DELETE SET NULL,  -- 使用者，可追溯邀请关系
    status      SMALLINT NOT NULL DEFAULT 0,        -- 0 未使用 / 1 已使用 / 2 已作废
    expire_at   TIMESTAMP NOT NULL,
    used_at     TIMESTAMP,
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE UNIQUE INDEX IF NOT EXISTS uk_invite_code ON ai_invite_code (code);
CREATE INDEX IF NOT EXISTS idx_invite_creator ON ai_invite_code (created_by, status);
```

生成规则：`SecureRandom` + 8 位字符集 `23456789ABCDEFGHJKMNPQRSTUVWXYZ`（去掉 0/O/1/I/L），
生成时查重，唯一索引兜底。

参数（常量，与 `AuthServiceImpl` 既有风格一致）：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `INVITE_EXPIRE_DAYS` | 7 | 有效期，过期未用即失效 |
| `INVITE_MAX_ACTIVE_PER_USER` | 5 | 每人"未使用"状态的码最多 5 个，作废不占额 |

### 3.2 接口（均需登录，复用 `AuthAspect` 现有 401 机制）

| 接口 | 说明 |
| --- | --- |
| `POST /api/auth/invite/create` | 生成邀请码。先校验本人未使用数量 < 上限；返回 `{code, expireAt}` |
| `GET /api/auth/invite/list` | 本人全部邀请码；`status` 为**计算值**：未使用但已过 `expire_at` 返回"已过期"，不跑定时任务 |
| `POST /api/auth/invite/revoke` | 作废本人未使用的码：`UPDATE ... SET Status=2 WHERE Id=? AND CreatedBy=? AND Status=0` |

注意：这三个路径**不要**加进 `JwtFilter`/`AuthAspect` 的 `SKIP_PATHS`，即自动要求登录——这正是"邀请码必须由已登录用户建立"的实现方式。

### 3.3 注册流程改造（`AuthServiceImpl.register`）

`RegisterRequest` 增加 `inviteCode` 字段。现有校验顺序不变，在"用户名唯一性校验"之后插入：

```text
1. inviteCode 为空 → 抛"注册需要邀请码"
   例外：userMapper.countUsers() == 0（全新库首个用户，无人能发码）放行
2. 查码：不存在 / Status=2 / 已过期 → 抛"邀请码无效或已过期"（统一提示，不暴露区分）
3. 条件占用（防两人并发用同一码）：
   UPDATE ai_invite_code SET status=1, used_by=?, used_at=now()
   WHERE code=? AND status=0 AND expire_at > now()
   受影响行数 != 1 → 抛"邀请码无效或已过期"
4. 插入 "User"（原逻辑不变，含 Snowflake ID、IP 注册限制）
```

方法加 `@Transactional`：占用码与插用户同一事务，插用户失败整体回滚，码自动还原为未使用。
原有"同 IP 每天最多 5 个"限制继续生效，在邀请码校验**之后**执行（顺序无所谓，但要在插库前）。

> 首用户引导的备选方案：不做空库放行，改为 README 提供一条手工 INSERT 首个邀请码的 SQL。
> 推荐**空库放行**：全新部署零手工步骤，且仅当库中无任何用户时触发，风险可控。

## 4. 密码错误累计与验证码

### 4.1 Redis Key 设计

| Key | 值 | TTL | 写入时机 |
| --- | --- | --- | --- |
| `login:fail:<username>` | 失败次数 | 30 天，每次失败续期 | 仅"账号存在且密码不匹配"时 INCR |
| `login:captcha:<uuid>` | 4 位大写答案 | 5 分钟 | 生成验证码时 |

- "累计、登录成功清零"：登录成功 `DEL login:fail:<username>`；平时**不做任何自动清零**，
  30 天 TTL 仅防 Redis 留存死键（每次失败续期，活跃账号永不过期）。
- 账号不存在**不计数**：没有可保护的账号，且对外提示与密码错误一致，不产生枚举信号。
- 验证码**校验即消费**（对错都 DEL）：一次性防重放；输错就刷新重输，由已有 IP 限流（10 次/分）兜底刷接口。

### 4.2 登录流程改造（`AuthServiceImpl.login`）

阈值常量 `LOGIN_FAIL_CAPTCHA_THRESHOLD = 5`。在第 2 步参数校验后插入：

```text
1. IP 限流（不变）
2. 参数校验（不变）
3. user = getByUsername(username)
4. failCount = GET login:fail:<username>
5. if failCount >= 5:                          // 强制验证码，先于验密码
       captchaCode 缺失 或 Redis 中答案不匹配
       → 返回 4001 {needCaptcha:true, failCount}
6. 密码不匹配:
       INCR login:fail:<username>（首点 EXPIRE 30 天，之后续期）
       → 抛"账号或密码错误"（已达阈值时 msg 追加"，请输入验证码"）
   账号不存在:
       → 抛"账号或密码错误"，不计数
7. 封禁检查（不变，仍在密码通过后）
8. 登录成功 → DEL login:fail:<username> → issueTokens（不变）
```

注意第 5 步放在验密码**之前**：次数达到阈值后即使密码正确也必须先过验证码，
验证码错误同样返回 4001 且**不计入**密码失败次数。

### 4.3 验证码接口（免登录）

`GET /api/auth/captcha`，返回 `{captchaId, svg}`，SVG 由 Java 原生拼接（无第三方库）：

```java
// 4 位 SecureRandom 字符（同邀请码字符集），SVG 内每字符独立随机
// 旋转 ±25°、深浅随机配色、2~3 条随机干扰线；答案以大写存入
// login:captcha:<captchaId>，TTL 5 分钟
```

**`/api/auth/captcha` 必须同时加进 `JwtFilter` 和 `AuthAspect` 两处 `SKIP_PATHS`**
（两份白名单独立维护，漏一处都会被 401 挡住——这是本项目免登录接口的既有约定）。

### 4.4 业务码约定与前端透传

- `4001`：需要验证码 / 验证码错误，`data = {needCaptcha: true, failCount: n}`。
- `request.js` 响应拦截器"其他错误"分支（`request.js:116`）改为把 code/data 挂到 Error 上再 reject：

```js
const err = new Error(res.msg || '请求失败')
err.code = res.code
err.data = res.data
return Promise.reject(err)
```

对既有调用无影响（它们只读 `error.message`），`Login.vue` 据此感知 4001。

## 5. 前端改动

### 5.1 Login.vue — 登录侧

- 组件内本地 `failCount` 计数：每次"账号或密码错误"（500）+1，达到 5 展开验证码行——
  与后端 4001 强制校验互为双保险（刷新页面后本地计数丢失没关系，后端仍会拦）。
- 验证码行：`el-input` + 右侧 SVG 图片，点击图片重新拉取；登录失败（4001）后自动刷新验证码；
  登录成功后重置本地计数、隐藏验证码行。
- 登录请求 payload 按需携带 `captchaId`、`captchaCode`。

### 5.2 Login.vue — 注册侧

- 新增"邀请码"输入框，注册模式必填，格式校验 8 位字符集；
  切换到注册模式时不预填，占位文案"邀请码（向已有用户获取）"。

### 5.3 邀请码管理入口（已登录用户）

- `MainLayout.vue` 顶栏用户区下拉新增「我的邀请码」→ `el-dialog` 弹窗：
  列表（码、状态、创建/过期时间、使用者）+ 每行"复制/作废" + 顶部"生成邀请码"按钮；
  未使用码数量达 5 时生成按钮禁用并提示。
- `api/index.js` 新增：`getCaptcha`、`createInviteCode`、`listInviteCodes`、`revokeInviteCode`。

## 7. 测试要点

邀请码：正常注册、码过期、码已用、码作废、并发同码仅一人成功、未登录建码返回 401、
本人未使用满 5 拒绝生成、空库无码注册放行、同 IP 5/天与邀请码校验共存、
插用户失败后码还原为未使用（事务回滚）。

验证码与计数：失败 4 次不出验证码、第 5 次起强制、验证码正确后密码错误继续计数、
验证码错误/过期/重放均 4001 且不计入密码错误、登录成功清零（连续 6 错 1 对再错不出验证码）、
30 天 TTL 与续期、账号不存在不计数、`GET /api/auth/captcha` 免登录可达、IP 限流共存。

前端：本地计数与后端 4001 双触发展开验证码行、点击刷新验证码、登录成功隐藏并重置、
邀请码弹窗各状态展示与复制、注册缺邀请码被前后端双重拦截。

## 8. 风险与回滚

- **回滚**：新逻辑集中在 `AuthServiceImpl` 插入的校验段与新增类，回退代码即可；
  `ai_invite_code` 表与 Redis 计数键保留无害，无需清理脚本。
- **误伤真实用户**：验证码只针对"密码错误满 5 次"的单账号，不影响他人；忘了验证码可点击刷新，
  密码想起来了直接登录成功即清零。
- **首用户空库放行被滥用**：仅当 `"User"` 表为 0 行时生效，生产库一旦有第一个用户即自动关闭；
  叠加既有"同 IP 每天 5 个注册"限制。
