1总览：两条路径怎么选

规则只有一条：打包必须在有 Node/JDK/Maven 的 Windows 上做，构建镜像必须在装了 Docker 的机器上做。这两件事未必在同一台机器。

反过来，Windows 上构建出的镜像与在服务器上构建的完全等价（都是 Linux 容器镜像，与构建机宿主系统无关）。

2一次性准备

2.1 在 Docker Hub 建私有仓库

  1. 登录 hub.docker.com；
  2. Create repository；
  3. Name 填 bizlens-ai，Visibility 选 Private；
  4. 仓库全名即 <账号>/bizlens-ai，脚本参数里的账号就是它。

2.2 生成 Access Token

Docker Hub 的 CLI 登录不再接受账号密码，密码位置必须填 Token：

  1. Account Settings → Personal access tokens → Generate new token；
  2. 权限选 Read & Write（只拉取的服务器可给 Read）；
  3. 生成后立即复制保存，页面关闭后不再显示。

2.3 登录：用到 docker 的机器都要做一次

docker login -u <账号>
# Password 处粘贴 Access Token，成功提示 Login Succeeded

2.4 路径 B 额外准备：Windows 的打包环境 + 服务器

机器需要安装
WindowsGit Bash（Git for Windows 自带）、Node 18/20 + pnpm、JDK 8、Maven 3.8+
服务器Docker + Docker Compose、tar（系统自带）。不需要 git、Node、JDK、Maven——脚本与 jar 由部署包带上来

私有仓库的安全边界：镜像内含后端 class 文件、前端产物与开发配置，被授权拉取的人可以解包查看。私有仓库只保证"未授权拉不到"，不等于加密。本方案的数据库口令、Redis 口令、AES 密钥、JWT 密钥全部在运行时通过环境变量注入，不进镜像。

3打包 jar（Windows，必做）

两条路径都要先打包。路径 A 由 release.sh 自动完成；路径 B 需手工执行，并把生成的部署包传到服务器。

# Windows，Git Bash，仓库根目录
bash docker/package.sh

脚本依次：pnpm install --frozen-lockfile → pnpm run build → 把 web/dist 复制进 svc/src/main/resources/static → mvn -pl svc -am clean package -DskipTests → 清理临时的 static 目录。

产物
路径内容
svc/target/bizlens-ai-service-0.0.1-SNAPSHOT.jar后端 + 前端静态资源 + application-prod.yml，约 140MB
web/dist/前端构建中间产物，已在 .gitignore 中

路径 B：把部署包传到服务器

package.sh 在打完 jar 后会顺手生成 bizlens-deploy.tar.gz，里面就是服务器构建与运行所需的全部文件。服务器不需要装 git、Node、JDK、Maven，也不需要拉仓库。

部署包内容（传一个文件即可）

# ① Windows：上传部署包
#   -O 用旧版 SCP 协议（NAS / 老 OpenSSH 的 SFTP 子系统不可用时需要）
#   -v 打印详细过程，排查连接与权限问题时很有用；-P 大写指定 SSH 端口
scp -O -v -P 19992 bizlens-deploy.tar.gz zzzoooo2@zzzoooo2.top:/vol1/1000/app/

# ② 服务器：解包并确认到位 —— 只传压缩包不算装好，这一步不能跳
#   解包目录必须就是 /vol1/1000/app，脚本按 svc/ 与 docker/ 的相对结构找文件
cd /vol1/1000/app
tar -xzf bizlens-deploy.tar.gz
chmod +x docker/*.sh          # 补执行位（包内本是 755，用 GUI 工具解包可能丢）
ls -l docker/release.sh docker/docker-compose.yml svc/target/*.jar   # 三个都在才算就绪

解包后的目录结构如下。脚本按这套相对结构找文件，请不要手工挪动：

/vol1/1000/app/
  svc/
    Dockerfile
    entrypoint.sh
    .dockerignore
    target/bizlens-ai-service-0.0.1-SNAPSHOT.jar
  docker/
    build.sh   push.sh   release.sh   run.sh
    docker-compose.yml
    .env.example        # 下一步复制成 .env

必须解到/vol1/1000/app/（或别的目录也行，只要 svc/ 与 docker/ 的相对关系不变），否则脚本找不到 jar。

若只想单独传 jar，必须放到 <部署目录>/svc/target/ 下；直接丢在部署根目录会报「未找到 svc/target/bizlens-ai-service-*.jar」。

若 scp 报 unknown option -- O，说明本机 OpenSSH 太老（-O 需 9.0+），去掉该参数即可。

打包会把前端产物临时写进 src/main/resources/static，结束即删除，git status 不会留残留。bizlens-deploy.tar.gz 在 .gitignore 中，不会进版本库。

4构建镜像（在装了 Docker 的机器上）

路径 A：Windows 有 Docker Desktop

确认 Docker Desktop 已启动（托盘图标运行中），然后在仓库根目录：

# 打包 + 构建 + 推送，一条命令；标签自动生成
./docker/release.sh <账号>

# 若 ./ 方式提示没有执行权限，就用 bash 显式调用
bash docker/release.sh <账号>

路径 B：Windows 无 Docker Desktop，在服务器上构建

部署包已解到 /vol1/1000/app/（见第 3 节），在服务器的该目录下执行：

# 用现成 jar 构建 + 推送，不重新打包（用 bash 调用，不依赖执行位）
bash docker/release.sh <账号> --skip-package

--skip-package 是关键：服务器上没有 Node/JDK/Maven，这个参数让脚本跳过打包，直接用传上来的 jar。服务器只要能访问 Docker Hub 即可。

只构建、先在本机验证可选

# 构建但不推送
REGISTRY=<账号> ./docker/build.sh

# 或从零到构建、不推送（打包 + 构建）
./docker/release.sh <账号> --no-push

# 构建完本机试跑（前台运行，Ctrl+C 停止；需先备好 docker/.env）
docker run --rm -p 10611:10610 --env-file docker/.env <账号>/bizlens-ai:latest

build.sh 依次校验：镜像命名空间已指定 → jar 存在 → jar 内确实含前端产物与生产配置 → Docker daemon 可用，然后才 docker build。

可覆盖的参数
参数默认值说明
REGISTRY（空，必填）Docker Hub 账号名；自建仓库填完整前缀，如 harbor.xxx.com/bizlens
IMAGEbizlens-ai镜像名，须与网页端建的仓库名一致
TAG（空）标签。留空即自动生成（见下方「标签从哪来」）
BASE_IMAGEeclipse-temurin:8-jre基础镜像（公共 JDK8 运行环境）；镜像内没有 git 时 Dockerfile 会自动安装

标签从哪来

Docker 自身不会生成版本号——docker build 不带 -t 只会产出一个没有名字的悬空镜像（只有 sha256 镜像 ID），这种镜像无法按名字推送。所以标签由 release.sh 生成：

四种写法
命令得到的标签是否同时更新 latest
./docker/release.sh <账号>自动时间戳，如 20261009-1435是
./docker/release.sh <账号> --gitgit 提交短哈希，如 0c75e8d是
./docker/release.sh <账号> 1.0.0你指定的 1.0.0否
TAG=1.0.0 ./docker/release.sh <账号>同上否

自动生成的两个好处：标签天然唯一且按时间有序，回滚时一眼就能找到上一版；同时把 latest 指向它，服务器上直接 bash docker/run.sh 就是最新版，不用记版本号。

--git 适合"这个镜像到底对应哪次提交"要能查的场景；latest 不被更新，意味着显式发布 1.0.0 时不会悄悄改变服务器下次拉取的结果。

构建上下文只有 svc/（配合 svc/.dockerignore 实际只传 jar），所以 web/node_modules 不会被送去 Docker，中文文件名（如本文档）也不在上下文里，不影响构建。

5推送到私有仓库

推送由 push.sh 负责，release.sh 已自动调用；只补推或换标签时才需要单独执行。

# 推送指定标签
./docker/push.sh <账号> 1.0.0

# 同时把 latest 指向该版本（新环境可直接拉 latest）
./docker/push.sh <账号> 1.0.0 --latest

# 也可用环境变量传参
REGISTRY=<账号> TAG=1.0.0 ./docker/push.sh

脚本会先校验：账号命名空间已指定 → Docker daemon 可用 → 本地确实有这个镜像（没有会提示先跑 build.sh，而不是丢一个看不懂的 push 错误），然后才推送。

push.sh 参数
参数说明
<账号>必填，Docker Hub 账号名
<标签>可选，默认 latest
--latest推送后再把 latest 指向同一版本

标签使用建议

  • 日常直接用自动生成的标签——时间戳唯一且按时间有序，一次上线一个标签，回滚时好找；
  • 要按语义版本管理就显式给 1.0.0 这类标签；要能查"镜像对应哪次提交"就用 --git；
  • latest 由自动生成的发布更新，显式指定标签时不动 latest；
  • 同名标签重复推送会覆盖旧镜像，正在运行的容器不受影响。

6服务器：用 docker compose 启动

6.1 登录（私有仓库必须）

docker login -u <账号>    # Password 填 Access Token

不登录直接拉取会报 unauthorized: authentication required。凭证保存在 ~/.docker/config.json，重启后一般仍有效。若构建也在本机做过，这步已跳过。

6.2 准备环境变量

cp docker/.env.example docker/.env
vi docker/.env
环境变量（必填项缺一个，容器启动即失败并明确报出来）
变量必填说明
REGISTRY是Docker Hub 账号名，脚本据此拼镜像名
DATABASE_URL是形如 jdbc:postgresql://zzzoooo2.top:53309/bizlens（容器里不能写 localhost，见常见问题）
DATABASE_USERNAME是数据库账号
DATABASE_PASSWORD是数据库口令
REDIS_HOST是Redis 地址
REDIS_PORT是Redis 端口
REDIS_PASSWORD否可为空
AES_KEY建议Git 令牌加解密密钥，32 位以上；不传退化为源码内置开发密钥
JWT_SECRET建议登录态签发密钥，32 位以上；不传退化为源码内置开发密钥
AI_EMBEDDING_*否语义召回，不启用则只走关键词召回
BIZLENS_GIT_PROXY否索引克隆仓库的出网代理，默认直连
BIZLENS_GIT_NO_PROXY否不走代理的地址，内网 Git 地址必须写进来，否则会 502
HOST_PORT否宿主机端口，默认 10610
TAG否要拉取的标签，默认 latest

格式必须是纯 KEY=VALUE：不要写 export、不要加引号。脚本会先做一次 CR 清理再读取，格式本身仍按此要求写。

6.3 启动：docker compose推荐

服务由 docker/docker-compose.yml 定义，启动就是一条 compose 命令。run.sh 是它的包装（多做两件事：启动前校验环境变量、启动后等就绪）：

bash docker/run.sh              # 校验 .env → compose pull → up -d → 等就绪
bash docker/run.sh --recreate   # 强制重建容器

# 等价的手工 compose 命令（先 cd 到 docker/，.env 就在那里）
cd docker
docker compose pull
docker compose up -d

临时换版本或端口不必改 .env，命令行传入即可（优先级高于 .env）：

TAG=20261008-1712 bash docker/run.sh    # 起指定版本（回滚常用）
HOST_PORT=8080 bash docker/run.sh       # 换宿主机端口

6.4 compose 文件说明

docker/docker-compose.yml 关键项
项作用
image由 .env 的 REGISTRY 与 TAG 拼出，即 <账号>/bizlens-ai:<标签>
container_name固定为 bizlens-ai，所以 docker logs/exec bizlens-ai 也能直接用
ports宿主机 HOST_PORT 映射到容器 10610
environment逐个列出容器需要的变量，取值统一来自 .env（不用 env_file 整体注入，避免 Windows 换行符混进值里）；必填项缺失时 compose 直接报「请在 docker/.env 中设置 xxx」
restartunless-stopped：进程崩溃或机器重启后自动拉起
loggingjson-file 轮转，单文件 10MB、保留 3 个，避免日志长期增长占满磁盘
健康检查沿用镜像内的 HEALTHCHECK（调 /api/system/health），docker compose ps 可见 healthy

6.5 运维命令

# 在 docker/ 目录下执行
cd docker
docker compose ps          # 状态 + 健康检查结果
docker compose logs -f     # 跟踪日志
docker compose restart     # 重启
docker compose down        # 停止并删除容器
docker compose up -d       # 按当前 .env 重新拉起

ports 左边是宿主机端口、右边是容器端口。容器内固定监听 10610，一般只改 HOST_PORT；前端请求都是同源相对路径，换端口不需要重新打包。要让容器内也换端口，得同时改 PARAMS、compose 的端口映射和 Dockerfile 健康检查里的端口，不推荐。

7验证与日常运维

# 容器状态与端口映射，以及健康检查结果
cd docker && docker compose ps

# 服务探针（重点看 database 字段）
curl http://zzzoooo2.top:10610/api/system/health

# 首页（应返回前端 index.html）
curl -I http://zzzoooo2.top:10610/

# 启动日志（含入口脚本打印的连接目标）
cd docker && docker compose logs -f

浏览器打开 http://zzzoooo2.top:10610/ 即见登录页，前端页面与后端接口在同一端口下，无需额外前置代理。若域名无法从服务器自身回环访问，上面两条 curl 的地址换成 127.0.0.1 即可。

探针的 status 有两个值：UP 正常，DEGRADED 表示它刚执行的 SELECT 1 没查到数据库（此时 database: DOWN）。两者 HTTP 都是 200，所以 容器显示 healthy 只说明 Web 服务在响应，不代表数据库通——排障时务必看返回体的 database 字段。

启动日志会打印生效的 DATABASE_URL、DATABASE_USER、REDIS（不含口令），便于确认连的是不是目标环境。出现「缺少必需的环境变量」说明 docker/.env 有遗漏；「未设置 AES_KEY / JWT_SECRET」只是提醒，容器仍会启动。

8版本升级与回滚

应用无状态（会话缓存在 Redis，索引临时目录随容器销毁），升级就是换镜像重启容器。

# 路径 A：Windows 有 Docker，一条命令出新版本（标签自动生成）
./docker/release.sh <账号>

# 路径 B：Windows 打包并生成部署包，服务器解包后构建推送
bash docker/package.sh                              # Windows：产出 bizlens-deploy.tar.gz
scp -O -v -P 19992 bizlens-deploy.tar.gz zzzoooo2@zzzoooo2.top:/vol1/1000/app/
cd /vol1/1000/app && tar -xzf bizlens-deploy.tar.gz    # 服务器：覆盖旧文件，docker/.env 不在包内、会保留
bash docker/release.sh <账号> --skip-package             # 服务器：构建 + 推送

# 服务器：compose 拉新镜像并起容器（latest 已被上次发布更新）
bash docker/run.sh

# 想按语义版本发布（且不改变 latest 指向）时显式给标签
./docker/release.sh <账号> 1.0.1

回滚

两种方式效果相同：临时回滚用命令行传 TAG，长期固定就改 .env 里的 TAG。两者都会重新拉取该版本并起容器。

# 看有哪些历史版本可用
docker images | grep bizlens-ai

# 方式一：临时回滚，不改配置文件
TAG=20261008-1712 bash docker/run.sh

# 方式二：长期固定在某个版本
vi docker/.env          # 把 TAG=latest 改成 TAG=20261008-1712
bash docker/run.sh

旧镜像仍在私有仓库与本地，回滚不需要重新构建。若要长期保留某个版本，用显式标签（1.0.0）发布更稳妥。

数据库变更

容器不会自动执行 SQL 迁移。若版本涉及表结构变更，需先按 svc/src/main/resources/db/ 下的脚本在目标库手工执行，再启动新容器。新建库用 schema-postgresql.sql；已有库按序号执行 migration-*.sql（可重复执行）。

9常见问题

打不开或选不了路径
现象原因与处理
Windows 上没装 Docker Desktop，能不能构建？ 可以，但不在 Windows 上构建。走路径 B：Windows 只 package.sh 打包，把 jar 传到服务器，在服务器上 ./docker/release.sh <账号> <标签> --skip-package。服务器上构建不需要 Node/JDK/Maven。
error during connect: ... dockerDesktopLinuxEngine 这台机器上的 Docker 没跑起来。装的是 Docker Desktop 就先启动它；本机压根没装就改用路径 B。
Docker Desktop 启动时提示 WSL2 相关错误 按提示安装 WSL2 内核并重启；或在设置里把后端切到 WSL2。企业机器若禁用了虚拟化，需要先在 BIOS 打开 VT-x/AMD-V。
PowerShell 里执行 ./docker/release.sh 报错 脚本是 bash 脚本，请在 Git Bash 里执行（Git for Windows 自带）；也可 bash ./docker/release.sh 账号 1.0.0。
Linux 上 ./docker/run.sh 提示 Permission denied git 在 Windows 上不记录执行位。服务器上执行一次 chmod +x docker/*.sh，或统一用 bash docker/run.sh。
构建与打包
现象原因与处理
版本号能省略吗？Docker 会不会自己生成标签？ 能省略，但标签不是 Docker 生成的——Docker 不带 -t 只会产出无名镜像（只有 sha256 镜像 ID），无法按名字推送。省略版本号时由 release.sh 生成时间戳标签（如 20261009-1435）并同时更新 latest；想按提交号区分就加 --git。
未找到 bizlens-ai-service-*.jar 还没打包，或路径 B 忘了传 jar。执行 bash docker/package.sh 并确认服务器上 svc/target/ 里有该文件。
提示 jar 内未找到前端产物 / 生产配置 用的是旧 jar 或前端构建失败。重新执行 bash docker/package.sh，确认结尾打印「完成：…jar」。
未指定镜像命名空间 REGISTRY 没传账号。用 release.sh <账号> <标签>，或 REGISTRY=<账号> 再跑 build.sh。
构建缓存/旧镜像占满 C 盘 docker system df 看占用，docker system prune -a 清理无用镜像与缓存（会删掉未使用的镜像，慎用）。
提示 digital envelope routines::unsupported Node 版本过高导致的老 webpack 报错（本项目 Vite 构建一般不会遇到）。确认 Node 为 18 或 20。
换行符 CRLF 导致容器起不来（/bin/sh^M） 仓库已带 .gitattributes，clone 出来就是 LF，正常不会有这个问题。只有用记事本手工改过脚本才会出现：sed -i 's/\r$//' svc/entrypoint.sh docker/*.sh。Dockerfile 里另有一道 CR 清理兜底。
推送与登录
现象原因与处理
本地没有镜像 <账号>/bizlens-ai:xxx 还没构建，或构建时用了别的账号/标签。先 REGISTRY=<账号> TAG=<标签> ./docker/build.sh，再推送。
unauthorized: incorrect username or password 用了账号密码登录。CLI 登录必须用 Access Token（网页端 Account Settings → Personal access tokens），粘贴到 Password 位置。
denied: requested access to the resource is denied 命名空间不对或未登录。<账号> 必须与你登录的 Docker Hub 账号一致。
repository does not exist or may require 'docker login' 仓库不存在。先在 Docker Hub 网页端创建名为 bizlens-ai 的私有仓库。
服务器 pull 报 unauthorized: authentication required 私有仓库需先在服务器执行 docker login（用 Token）。
推送或拉取很慢、超时 Docker Hub 网络问题。可给 daemon 配 registry mirror（Windows 在 Docker Desktop 设置里改，Linux 改 /etc/docker/daemon.json），或在一台能出网的机器上 docker pull 后 save/load 中转。
服务器运行阶段（docker compose）
现象原因与处理
服务器上执行 sudo ./docker/release.sh 报 command not found（或 No such file or directory） 两种原因，ls -l docker/release.sh 一看便知：① 没解包——只把 bizlens-deploy.tar.gz 传上来了，这个路径下没有该文件，先按第 3 节 tar -xzf 解包；② 文件在但没有执行位（权限显示 -rw-r--r--），chmod +x docker/*.sh 即可。不想管执行位就直接 bash docker/release.sh；需要 root 跑 docker 就用 sudo bash docker/release.sh——bash 方式不依赖执行位，最稳。
找不到 docker compose 命令 本机没装 compose 插件。Docker Desktop 自带；Linux 上装 docker-compose-plugin。run.sh 会自动在 docker compose 与老版的 docker-compose 之间择一，两者都没有才会报错。
compose 报 Unsupported config option for services 本机是 Compose v1（docker-compose），读不了本文件。升级到 compose v2 即可。
compose 报 required variable REGISTRY is missing a value: 请在 docker/.env 中设置… docker/.env 不存在，或该项为空。补齐后重跑。注意此时连 docker compose down 也会因同一原因报错，急着停容器可直接 docker rm -f bizlens-ai。
docker compose ps 显示 healthy，但页面接口报错 健康检查只看 Web 服务有没有响应。数据库不通时探针仍返回 HTTP 200（status: DEGRADED），要 curl 探针看 database 字段。
容器反复重启，日志报缺少必需的环境变量 docker/.env 少了数据库或 Redis 项，补齐后重跑 run.sh。
日志报 Could not resolve placeholder 启动命令漏传环境变量。DATABASE_URL、DATABASE_USERNAME、DATABASE_PASSWORD、REDIS_HOST、REDIS_PORT 五项必填。
页面能打开但接口报错，探针返回 database: DOWN 容器里的 127.0.0.1 是容器自身，不是宿主机。本环境的数据库也在 zzzoooo2.top 上，DATABASE_URL 里写 localhost／127.0.0.1 连不上——用域名（zzzoooo2.top:53309）或宿主机内网 IP。若域名解析到公网 IP 而服务器不支持回环访问，改用内网 IP，或在 compose 的 bizlens-ai 下加 extra_hosts: ["host.docker.internal:host-gateway"] 后把地址写成 host.docker.internal。
索引代码仓库报 502 或连不上 设了 BIZLENS_GIT_PROXY 却没把内网 Git 地址写进 BIZLENS_GIT_NO_PROXY，内网流量被送去代理了。
端口被占用（Port already in use） HOST_PORT=8080 ./docker/run.sh 换宿主机端口，或先停掉占用进程/旧容器。
前端页面打开是空白/资源 404 镜像里的 jar 没带前端产物，多半是构建时用了旧 jar。重新构建，并注意脚本开头的「已确认 jar 内含前端产物」提示。

docker/ 下的文件
文件在哪跑做什么
package.shWindows（需 Node/JDK/Maven）前端构建并并入 jar，Maven 打包出 jar，再打成部署包 bizlens-deploy.tar.gz
build.sh装了 Docker 的机器校验 jar 与 daemon，构建镜像（不推送）
push.sh装了 Docker 的机器校验后推送镜像，可选同时更新 latest
release.sh装了 Docker 的机器一条命令串起 打包 → 构建 → 推送
docker-compose.yml服务器服务定义：镜像、端口、环境变量、重启策略、日志轮转
run.sh服务器compose 的包装：校验 .env → pull → up -d → 等就绪
.env.example—环境变量模板，复制成 .env 供 compose 与脚本共用（已被 .gitignore 忽略）
